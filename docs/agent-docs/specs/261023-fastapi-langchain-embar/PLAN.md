# Plan: FastAPI, LangChain, and Embar migration

Status: approved
Revision: 4
Spec: SPEC.md revision 1 (approved)

## Approach
Keep SvelteKit as the presentation and SSR/form-action layer, replacing its business modules with a small server-only HTTP bridge to a Python FastAPI service. Python owns validation, authentication, persistence through Embar, and LangChain/OpenRouter text generation. Preserve PostgreSQL's existing schema and scrypt/session formats. Route browser API calls to Python through Vite during local development and Vercel Services in deployment, preserving original paths and the public origin.

## Data Model and Contracts

### Database access and compatibility
- Use Embar's documented `QuerySingle(sql, params)` with `AsyncPgDb.fetch()` and `execute()` for existing PostgreSQL-specific UUID and timestamptz contracts. SQL is a fixed application-owned string with named placeholders; values are passed separately in the params mapping. Validate returned dictionaries with the existing Pydantic row models. Embar's `db.sql(t"...")` interpolates identifiers only, and must never receive ordinary user values. Query builders remain available where suitable. Psycopg provides transport/pooling and explicit management commands, with runtime CRUD issued through Embar.
- Preserve `images`, `users`, `sessions`, `health_profiles`, `dishes`, and `meals`, their UUID primary keys, defaults, JSONB ingredient arrays, FK cascades/set-null behavior, and timestamps. SQL aliases or model serialization expose the existing camelCase frontend fields.
- Connection values come from the six existing environment keys. Support optional `PGPORT` and `PGSSLMODE` (SSL defaults to `require`, matching existing behavior). Use safe conninfo construction, bounded pool (max 10), connect timeout, and disabled prepared statements for pooler compatibility. No dotenv loading or connection occurs on module import. Application startup never migrates or seeds.
- Passwords retain `salt:hash` hex, with scrypt N=16384, r=8, p=1, dklen=64 and the literal hex salt string as the salt bytes. Session cookies remain random URL-safe tokens, SHA-256 hex stored in `sessions`, expiring after seven days. Normalize account email by trim/lowercase, check existing emails case-insensitively and handle unique-violation races. All newly inserted accounts use lowercase, so differently-cased concurrent requests collide on the existing unique constraint.
- Profile writes use a single upsert after complete validation. Meal reads/deletes always constrain owner id. Validate optional source dish and treat malformed/absent/nonexistent source references as null; protect against concurrent source deletion without exposing FK errors.
- Fresh/test setup explicitly applies preserved historical migrations in order with a ledger; refuse conflicting preexisting unmanaged tables rather than replay DDL against production. The command must explain how an existing managed application database requires no setup. Seed uses deterministic UUIDs (UUIDv5 from a fixed namespace and dish name) and conflict-do-nothing for ids. Also skip dishes with an existing exact name so legacy randomly generated ids remain untouched. Missing images use the existing deterministic ids and conflict-do-nothing. Repeat invocations preserve IDs/references and never update or delete catalog records.

### HTTP API
- `GET /api/health`: lightweight readiness response, no database or AI call.
- `GET /api/auth/session`: `{user: {id,email} | null}`. `POST /api/auth/register` accepts `{email,password,confirmPassword}`, returns 201 `{user}` and cookie. `POST /api/auth/login` accepts credentials, returns 200 `{user}` and cookie. `POST /api/auth/logout` destroys the session and returns 204 with cookie deletion.
- `GET /api/profile`: `{profile}`. `PUT /api/profile`: accepts the existing camelCase fields and returns `{profile}`. Both authenticated.
- `GET /api/dishes`: `{dishes}` in name order with image locations. `GET /api/dishes/{id}`: `{dish}` with ingredients, content, camelCase metadata. Both authenticated.
- `GET /api/meals`: `{meals}` newest first. `GET /api/meals/{id}`: `{meal}`. `POST /api/meals`: existing `{title,content,sourceDishId?}`, 201 `{id}`. `DELETE /api/meals/{id}`: 204. All authenticated and owner-scoped.
- `POST /api/adapt`: existing `{dishId}`, `text/plain; charset=utf-8`. Buffer first nonempty model text before creating `StreamingResponse`; absent text/provider/config failure returns 502 `{error}`. Subsequent provider failure aborts the stream, and the existing client catch leaves status idle with visible interruption and saving disabled. Close the model iterator on error, completion, or cancellation; do not emit provider exception text into recipes.
- Errors use JSON `{error: string, errors?: Record<string,string>}` and existing 400/401/404/502 status semantics. Handle malformed JSON and Pydantic type errors as 400 instead of FastAPI's default 422. Authenticate protected routes before parsing/validation. Generic unexpected failures do not expose DB credentials or stack traces.
- Reject mismatched Origin and cross-site mutation requests before processing cookie-authenticated writes. Define a trusted origin set from optional `APP_ORIGIN` (the canonical public origin) and the Vercel deployment hostname variables. Hosted mode means `VERCEL_ENV` is `production` or `preview`: add HTTPS origins for `VERCEL_URL` and `VERCEL_PROJECT_PRODUCTION_URL`, omit local defaults, and fail closed for unknown origins with 403. Development mode, including `VERCEL_ENV=development` from `vercel dev`, allows `http://localhost` and `http://127.0.0.1` on ports 5173, 3000, and 8000; a local `VERCEL_URL=localhost:3000` uses HTTP rather than HTTPS. A present Origin must exactly match a normalized allowed origin, and `Sec-Fetch-Site: cross-site` is rejected. Missing Origin is allowed for non-browser/server callers, while JSON-only body endpoints and absent permissive CORS prevent browser simple-request bypass. JSON endpoints require JSON for bodies; no permissive CORS configuration. Document `APP_ORIGIN` for custom domains and nondefault development ports.

### Frontend bridge and deployment
- The bridge uses native server `fetch` to a configured private `BACKEND_URL` for local Python (default `http://127.0.0.1:8000` in development) and the public request origin in production. Use native fetch, not SvelteKit's internally dispatched same-origin fetch, so production requests reach Services routing after TS API routes are removed. Forward only the session cookie, not arbitrary browser headers; never send it to a user-controlled URL. Mutation Origin is the public `event.url.origin` after SvelteKit has validated the incoming form origin; Python checks it against its trusted origin set. Browser-direct requests retain their Origin through the development proxy and Services routing, so checking never depends on an internal proxy Host.
- Forward only the known session cookie from backend auth responses through SvelteKit `cookies.set`/`delete` with the seven-day, HTTP-only, SameSite=Lax, path `/`, HTTPS-secure policy. Prevent credentials from being returned as action values. Map backend field errors into existing `fail` shapes and use friendly 502 service errors for unavailable Python. Protected page loaders/actions must check `locals.user` themselves where necessary because layout guards do not serialize child server loads.
- Root `vercel.json` declares frontend service `root: "./"` and backend service `root: "backend/", entrypoint: "main:app"`. First rewrite `/api/(.*)` selects backend, catchall selects frontend. Paths remain unchanged; this avoids the documented SvelteKit problem with rewrites changing page URLs. Keep adapter-vercel's Node runtime and explicitly select Python 3.14 in backend manifests.
- Local frontend Vite and preview `/api` proxies point to `BACKEND_URL`; use two documented processes, or `vercel dev` for Services. Runtime env loading may be documented for application commands but agents never inspect `.env` and verification sets isolated environment variables instead.

## Risks
- Embar requires Python 3.14; this environment currently has 3.13: provision a managed 3.14 interpreter and isolated venv before backend tests, with Vercel pinned to the same minor.
- Embar's built-in schema generation lacks legacy PostgreSQL-specific types: retain historical SQL and use typed parameterized Embar SQL. Verify real PostgreSQL round-trips for UUIDs, timestamps, JSONB, joins and returning ids.
- Hosted Services behavior requires a Vercel account: validate checked-in config and local same-origin behavior; label hosted deployment unverified until a real preview exists.
- Proxy/runtime buffering could mask partial-stream failures: verify first-text and mid-stream behavior over real HTTP through the frontend proxy, not only ASGI test clients.
- No PostgreSQL server is currently on PATH: provision an isolated test server outside application dependencies; never substitute the configured database for destructive tests.
- Existing tests mock obsolete TypeScript internals: replace them with bridge/API behavior tests as modules retire, retaining unrelated component coverage.
