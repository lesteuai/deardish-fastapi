## Overview
DearDish's backend currently runs inside SvelteKit with TypeScript database and AI integrations. Move backend behavior to Python using FastAPI, LangChain, and Embar while preserving the existing SvelteKit user experience and PostgreSQL data. Provide reproducible local development and Vercel full-stack deployment configuration.

## User Stories
- As an existing user, I want my account, active session, profile, catalog, and saved meals to remain usable after migration.
- As a user, I want the same registration, sign-in, profile editing, menu browsing, streaming adaptation, and meal management flows.
- As a maintainer, I want the Python backend isolated in a virtual environment and documented commands for development, checks, database setup, and deployment.

## Acceptance Criteria
- AC-1: The SvelteKit landing page, navigation, authentication forms, protected pages, dish images, original recipe content, and saved-recipe rendering remain available at their current page URLs. Anonymous protected-page visits redirect to `/auth/login`.
- AC-2: FastAPI owns authentication and backend data operations. Valid registration signs the user in; invalid email, passwords shorter than eight characters, mismatched confirmation, and case-insensitive duplicate email return visible field errors without creating an account. Invalid login creates no session. Logout invalidates the session. Session cookies remain HTTP-only, SameSite=Lax, scoped to `/`, secure on HTTPS, and expire after seven days.
- AC-3: Existing PostgreSQL users, password hashes, unexpired session tokens, profiles, dishes, images, and meals work without destructive reset, reseeding, or rewriting user records. Embar is the runtime database access layer, retaining existing table and column names and ownership constraints. Startup performs no schema changes or catalog writes.
- AC-4: Authenticated users can read and atomically update their own profile. Conditions, allergies, and dietary preferences accept optional trimmed text up to 200 characters each; notes accept up to 2000 characters. Invalid input returns field errors and leaves persisted values unchanged. Empty profiles remain usable.
- AC-5: Authenticated users can browse dishes in name order, view ingredients and original recipe content, and see available dish images. Malformed dish identifiers return 400 and unknown valid identifiers return 404. The catalog uses the existing database data.
- AC-6: `POST /api/adapt` uses LangChain with the configured OpenRouter model and streams plain UTF-8 recipe text using dish name, cuisine, description, ingredients, original recipe, and the user's profile. Empty profiles receive existing healthy-cooking guidance. The prompt preserves complete recipe sections and bolded changes. Anonymous requests return 401 JSON, malformed input returns 400 JSON, unknown dishes return 404 JSON, and missing configuration or provider failure before text returns friendly 502 JSON. A mid-stream provider failure produces a visible interruption error and prevents saving incomplete output; provider internals remain private.
- AC-7: Authenticated users can save, list, view, and delete their own meals. Titles are trimmed, nonempty, and at most 200 characters; content is nonempty. Save returns 201 with an id, delete returns 204, validation returns 400, anonymous API requests return 401, and access to another user's meal returns 404. Invalid meal identifiers return 404. Optional source-dish references are retained when valid and existing; malformed or nonexistent references cannot cause a server error or persist an invalid reference.
- AC-8: Python dependencies install into an ignored `venv` or `.venv` using Python 3.14. Dependency manifests and repeatable commands cover backend startup, lint, type checking, tests, schema setup, and non-destructive catalog seeding. `.env` is never read by agents or exposed in output; configuration key names come from `.env.example`, retaining `PGHOST`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`, `AI_API_KEY`, and `AI_MODEL`. Application processes may consume configured environment values without logging secrets.
- AC-9: Local development and checked-in Vercel configuration route `/api/*` to FastAPI and page/static requests to SvelteKit on one public origin. Server-rendered loads and form actions reach FastAPI with the current user's session and propagate authentication cookie changes. Private data and AI credentials stay in Python; SvelteKit retains only frontend/HTTP integration. Cookie-authenticated mutations reject foreign-origin requests. Deployment documentation follows the referenced Vercel full-stack Services template, including Python 3.14 selection.
- AC-10: Frontend and backend lint, type checks, and unit tests pass. End-to-end verification exercises every affected user flow, existing-format credentials/session compatibility, ownership, validation, and streaming success/failure through the integrated app using an isolated test database and controlled AI where needed. The frontend production build passes as the final validation command. Evidence distinguishes local verification from hosted deployment, which requires external deployment access.

## Edge Cases
- Expired, missing, or invalid sessions: anonymous behavior without exposing private records.
- Duplicate registration race: one account succeeds and the other receives the duplicate-email field error.
- Empty profile or missing profile row: empty fields and healthy-cooking fallback.
- Malformed JSON or wrong input types: friendly 400 JSON, with authentication checked first for protected APIs.
- Missing images: the existing page fallback remains functional.
- Source dish deleted or absent: optional meal reference remains null; meal content remains readable.
- Missing backend service: a friendly frontend service error, without credential or connection-string exposure.
- Mid-stream failure: partial text can remain visible, but saving is unavailable until a successful adaptation.

## Non-Goals
- UI redesign, new product capabilities, provider changes away from OpenRouter, database hosting changes, and changes to historical verified feature artifacts.
- Automatic migration or seed execution against the configured database during application startup.
- Creating a hosted Vercel deployment without deployment access.
